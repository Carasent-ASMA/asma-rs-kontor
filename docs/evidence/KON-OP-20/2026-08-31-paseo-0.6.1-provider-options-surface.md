# KON-OP-20 — is there a daemon-acknowledged per-agent OpenCode permission object in installed Paseo 0.6.1?

Task `01a02a7f-8e47-7682-be52-1b9f2a632ac4` (permission posture). **Not ASMA-7968.**
Read-only inspection of the installed bundle on 2026-08-31. Nothing was edited,
repacked, restarted or upgraded; no user global or project configuration was
touched; no seat or workspace was created, reloaded, archived or replaced. This
inspects **installed 0.6.1**, not upstream `getpaseo/paseo`.

Source read from `/Applications/Paseo.app/Contents/Resources/app.asar` by
offset, without extracting it.

## Answer

**A typed per-agent OpenCode permission object exists and is applied
provider-natively in the spawned session. A daemon acknowledgement *that it was
applied* does not exist.** OpenCode delivery therefore stays fail-closed.

## What exists — positive evidence

### 1. A typed, validated per-agent permission map

`@getpaseo/server/dist/server/server/agent/providers/opencode/options.js`:

- `OpenCodeProviderOptionsSchema` — a `.strict()` zod object whose `permission`
  field is OpenCode's own `Config.permission` shape (`read`, `edit`, `bash`,
  `task`, `external_directory`, `webfetch`, `websearch`, `skill`, `lsp`, …),
  each an action (`ask|allow|deny`) or a pattern→action record. The comment
  states it is "maintained against `@opencode-ai/sdk 1.14.46`".
- `buildOpenCodePermissionRules(options, toolPolicy)` flattens it to
  `{permission, pattern, action}` records — the same record shape OpenCode's own
  `fromConfig` produces.

### 2. It reaches the spawned OpenCode session

`providers/opencode-agent.js` calls
`buildOpenCodePermissionRules(this.config.providerOptions, this.config.toolPolicy)`
and passes the result as `permission` to
`this.client.session.promptAsync({ sessionID, directory, messageID, parts, …, permission, … })`
— on the ordinary prompt path and on the dispatch path. In the installed
OpenCode 1.18.15 binary, `SessionPrompt.prompt` sets the session's own rules from
that request (`O.permission = B; setPermission({sessionID, permission: B})`), and
the evaluator is called with the session's array
(`evaluate("task", name, U.permission)` and similar).

This is a provider-native policy delivered into the spawned process over the SDK.
It is **not** an environment variable, a config file, or anything ambient.

### 3. A protocol surface Kontor's adapter already speaks

`@getpaseo/protocol/dist/messages.js`:

- `hub.execution.agent.create.request` carries
  `providerOptions: ProviderOptionsSchema.optional()`, alongside `env`,
  `toolPolicy`, `mcpServers`, `worktree`.
- `hub.execution.agent.validate.request` carries `provider` + `providerOptions`
  and validates **without creating**.
- Both are members of `SessionInboundMessageSchema`, the WebSocket inbound union.
- `AgentSessionConfigSchema` carries `providerOptions` too.

### 4. Validation is enforced, with a typed refusal

`agent-manager.js` → `applyProviderConfiguration` throws
`Provider '<p>' does not accept providerOptions` when the definition has no
`validateOptions`, and otherwise runs `definition.validateOptions(...)`. The
create response can carry `provider_options_invalid` with zod issue paths.

## What does not exist — the acceptance-critical negative

**There is no applied-acknowledgement for `providerOptions`.**

- `HubExecutionAgentCreateResponseSchema.payload` contains
  `toolPolicyApplied: z.literal(true).optional()` — an explicit, per-field
  *applied* flag — and **no `providerOptionsApplied` counterpart**. The protocol
  therefore proves it can express "this policy was applied", and does so for tool
  policy only.
- `AgentSnapshotPayloadSchema` does **not** include `providerOptions`, so no
  readback of a created agent states the permission it is running under.
- Every occurrence of "acknowledge" in `opencode-agent.js` concerns **turn
  cancellation and abort** (`acknowledgeCancellation`, abort settlement), not
  policy application.

So a successful create with no `provider_options_invalid` proves the options
were **accepted and schema-valid**. It does not prove the spawned process
**applied** them, and nothing in the installed surface reports that it did.

## Verdict against the acceptance criteria

The surface is materially stronger than anything Kontor uses today, and would
replace the owned-config-root and its ambient-layer problem entirely. But the
criterion was a **daemon-acknowledged** object, with the acknowledgement proved
to be about the created process. That acknowledgement is absent, and none of the
substitutes are permitted: not CLI `--env`, not the daemon version, not a
preflight in kontord, not a static custom-provider env.

**OpenCode delivery remains fail-closed. Nothing was implemented on the strength
of this finding.** OP-20 remains in progress.

## What would close it

Any one of:

- a `providerOptionsApplied` (or equivalent) acknowledgement on
  `hub.execution.agent.create.response`;
- `providerOptions` echoed in `AgentSnapshotPayloadSchema`, so a readback states
  the applied permission;
- an OpenCode-side readback of a session's effective permission rules that Paseo
  surfaces.

With any of those, the smallest Kontor path is already visible: send the rendered
block as `providerOptions.permission` on the create request, treat
`provider_options_invalid` as a typed refusal, and require the acknowledgement
before binding — with hostile-ambient and zero-native-effect boundary tests, and
the existing destructive floor and exact-floor allowance rules unchanged.

# CURRENT DISPOSITION — 2026-08-31 (supersedes every status above)

**OpenCode delivery is reachable, in two proved stages, and is no longer
fail-closed.** Every earlier disposition in this file — the environment
approach, the owned configuration root, the spawn-environment attestation and
the refusal that rested on it — is superseded and the code implementing them is
deleted.

## What ships

`launch_admitted` branches for OpenCode alone; every other provider keeps the
CLI create it had, and Claude's worktree MCP composition is untouched.

1. Gates before any native call: the daemon must accept typed per-agent
   `providerOptions`, and the provider must express the declared posture.
2. `create_agent_request` with the rendered permission in
   `config.providerOptions.permission`, the MCP surface in `config.mcpServers`,
   a launch-intent digest label over the whole create configuration, and **no**
   `initialPrompt`.
3. A lost acknowledgement reconciles by exact-label census — one adopted, none
   confirmation-unknown, more than one refused — and the create is never resent.
4. The first real turn, with a message id derived from the launch; the daemon
   replays the persisted `providerOptions.permission` into `session.promptAsync`
   and OpenCode installs it before evaluating a tool call.
5. Binding only on an answer that names that request and that agent and says
   accepted. Otherwise: archive over the same socket, read back terminal, and a
   recoverable refusal if that cannot be confirmed.

## Why this is sound where the earlier approaches were not

The policy never passes through a file or an environment variable, so the merge
order that defeated every earlier design — global, project, `.jsonc` siblings,
`OPENCODE_*` variables, active-org remote config, managed profiles — has nothing
to act on. Acceptance of the turn is the acknowledgement, and it is about the
process that ran it.

## Not claimed

No live authenticating seat has been launched through this path. That is a
post-integration, post-deployment proof and is not asserted here.
