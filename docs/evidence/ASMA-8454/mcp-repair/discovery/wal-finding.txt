## When to Load

Load for the coordinator's WAL disposition or for the separately scoped shutdown follow-up. Do not use as authority to resume the rehearsal or alter a live realm.

## Finding and recommendation

Classify this as a **pre-existing shutdown/ownership defect**, not an ASMA-8454 regression. The source establishes a strong reference cycle: `ApiState` owns an `Arc<Services>` through `Applications`, and `Services::state` owns the same `ApiState`. That retains the SQLite store when the daemon value is consumed. Shutdown signals stop, releases the lock and logs success without breaking the cycle or explicitly closing/checkpointing the connection. The normal last-connection close therefore does not run through this ownership path. This is source analysis supported by real-process reproduction, not an instrumented destructor trace.

Recommend option **(i)**: approve an explicit stopped-realm export/check-WAL step using the already-supported released command, then resume the rehearsal under that documented procedure. Also record the reference cycle and incomplete shutdown closure as a separately owned follow-up. No repair, raw SQL checkpoint, journal-mode change, or manual WAL deletion was made. The original realm is still held pending the coordinator's decision.

The released bundled SQLite probe observes version **3.53.2**, WAL, automatic checkpoint threshold **1000 pages**, `journal_size_limit=-1`, `synchronous=2`, and `NO_CKPT_ON_CLOSE=false`. These are observations of a separate normal connection to an exact diagnostic copy, not a live query of the daemon's private connection. The configuration source sets no checkpoint overrides. Rusqlite's `InnerConnection` destructor calls `close()` (`rusqlite-0.40.2/src/inner_connection.rs:412`), which calls `sqlite3_close` (`:157`). Bundled SQLite's `sqlite3PagerClose`/`sqlite3WalClose` attempt a checkpoint and remove sidecars when eligible for exclusive last-connection close (`libsqlite3-sys/.../sqlite3.c:63794`, `:69964`). That is conditional behavior; every rehearsal must inspect the actual WAL after the supported command.
