# Selected fleet enforcement

Apply before launching, reusing, resuming, changing the brain of, or replacing
any workflow seat, including supervisors, advisors and reviewers. Recovery and
release authority do not grant model-selection authority. The selected fleet
owns provider, account route, model, effort, chain order and eligibility.

## Declare the fleet before placing seats

1. Read the project's explicitly selected config folder and its fleet reference
   (`{{ project.fleet }}`). Resolve the reference relative to that folder;
   record the absolute fleet location and content hash, role/slot binding and
   selection evidence in the owning plan or checkpoint. If the config exposes
   several fleet references, require them to identify the same selected policy.
2. Establish which revision governs this operation. On direct work, record the
   authorized fleet snapshot selected by the plan/config through the supported
   project procedure; no daemon is required. On governed work, read the selected
   activated revision through the owning control plane. A file's presence, a
   repository checkout or an authoring-only header does not prove selection.
   An explicitly retained valid snapshot remains evidence; do not silently
   switch to another checkout, newer file or runtime profile.
3. If selection, file, validity or binding is missing, state the exact gap:
   **a fleet must be selected, or created and selected, before this seat can
   proceed**. Name the searched config location and affected role. The owner
   locates and declares an existing fleet or prepares one through the project's
   fleet-authoring procedure within existing authority. Ask the operator only
   for an unresolved choice reserved to them. Never invent a roster or chain
   from the runtime's model catalog to get past this requirement.

## Resolve and verify every operation

- Resolve the declared role's chain from that selected revision. Respect its
  order, provider/account routes, effort, exclusions, capabilities and review
  independence. Availability can eliminate a route; it cannot authorize one.
  If no eligible route remains, hold that operation and name its owner and
  resumption condition. Continue unrelated eligible work.
- Use the shared resolver when qualified. Otherwise read and apply the same
  selected fleet explicitly and record the weaker procedural evidence. Never
  silently fall back to runtime defaults, an inherited session setting, a
  convenient profile or a model available in a tool's catalog.
- Supply the resolved route explicitly through the supported runtime operation.
  Before task effects or acceptance of a verdict, read back the effective
  provider/account route, model and effort against the selected binding. Missing,
  different or unverifiable values block that seat's task effects. Preserve its
  work and correct the route through the supported lifecycle; do not silently
  change an active writer or launch a duplicate.
- A resume checks the occupant against its valid recorded fleet revision; it
  does not inherit permission to use whatever model the session now reports.
  A replacement resolves its route afresh before retiring the predecessor.
  Fleet changes do not silently migrate running occupants or erase frozen pins;
  use the supported policy-selection and lifecycle transition.

## One policy source

Keep model rosters, allow/deny lists and fallback order in the fleet. Skills,
templates, heartbeat prompts, recovery mandates and handoffs point to its
location and revision; they do not hardcode model choices or incident-specific
blacklists. Record resolved model values as observed evidence, not copied
policy. A model change requires the owning fleet selection procedure.

The evidence is the fleet location/hash and selection reference, role binding,
considered routes and rejection reasons, resolved route and actual runtime
readback. These are mandatory workflow checks; skill prose alone does not
install a runtime validator or prove that an external launcher enforces them.
